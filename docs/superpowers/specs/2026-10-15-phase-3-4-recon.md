## 2. Where the map stops working

**Keep the five columns exactly as they are.** The map is an index of apt names that the release's own archive can resolve, and `where` is parsed by a `case` with literally `none|both|<release>`. Every non-`none` row is handed straight to `apt-get install -y`, and one unknown name fails the whole transaction — so a row spelling `docker-ce`, `dbeaver-ce`, `google-chrome-stable`, `teams-for-linux`, `dropbox` or `onlyoffice-desktopeditors` would not just fail itself, it would take its entire group down on a clean machine. Growing `where` to a `vendor` value would make the map describe a key, a URL, a suite, a pin and an update, and `map_group_packages` would need to stop being a lookup and start being an installer. That is the wrong place for it.

The one answer: **the map keeps two row shapes, and a second mechanism sits beside it — one `setup-<subject>.sh` per subject, sharing two new helpers in `lib/common.sh`.** That is not a new pattern; it is what `setup-nvim.sh` already does for Neovim and `setup-sway.sh` for the Sway group.

Three code changes the second mechanism needs, all small:

1. **`add_vendor_repo` in `lib/common.sh`.** Six subjects need the same sequence and copying it six times recreates exactly the defect the phase 1 review found. Contract: `install -d -m 0755 /etc/apt/keyrings`; fetch the key and only then write the sources file (a list file without its key is the one way this can damage a working system); its own `apt-get update`; then verify by candidate, not by exit status; on any failure **remove the sources file again** so the shared update stays clean. It must support both forms observed: a suite/components line (Google, Docker, Dropbox, Teams, ONLYOFFICE) and DBeaver's flat `… /` with the trailing slash, because `dbeaver.io/debs/dbeaver-ce/dists/` is 404. It must take an optional pin, because ONLYOFFICE's 308 stanzas over 71 names outrank the distribution's `ttf-mscorefonts-installer`.
2. **`try` in `lib/common.sh`.** `attempt` returns 0 unconditionally — by design — so there is today no way to record a failure *and* branch on it. Six steps need that branch: the key fetch before the list write, the ONLYOFFICE candidate check (its update exits 0 when the host is unreachable), the Postman version parse coming back empty, `sshd -t` before any restart, `findmnt -no FSTYPE /` before any snapshot work, and the Tor Browser signature check — where continuing with `attempt` after a failed verify would install unverified bytes.
3. **Stop excluding groups by name in `install.sh`.** The enumeration is `awk … $1 != "editor-tools" && $1 != "sway"`, and phases 3–4 add five groups (`docker`, `postman`, `conky-panel`, `snapshots`, `hardening`, plus whatever `office`/`chat`/`files`/`tor` carry) that belong to their own scripts — otherwise the i3 run starts offering Electron libraries and sshd. `group_label` already names exactly the six groups `install.sh` owns; make that table the source of truth and iterate over its keys instead. One change, and no filter to maintain again.

`tests/apt-map-smoke.js` needs nothing new structurally — the `chromium` pair is the second per-release split and the existing rule covers it — but `readme-smoke.js` will fail until every new installable name is documented.

## 3. What the installer must survive

The hard constraint comes from `install.sh` itself: `run sudo apt-get update` is deliberately fatal ("installing against a stale index is worse"). Once any vendor list file exists, that one line can abort the whole run on someone else's outage. Two rules follow, and they are not negotiable:

- **Every vendor step runs after the shared update/install, owns its own `apt-get update`, and removes its sources file on failure.** Then the next shared update is clean.
- **A failing shared update must say why before it stops.** Replace the bare `run sudo apt-get update` with a guarded block: on failure, name the third-party sources files this installer added and say that removing one restores the run. Same fatal outcome, plus the one fact the user needs — because after phase 3, a Google, Docker or Dropbox outage can block a *re-run* of a previously working installer.

Two failure modes exist and neither is caught by `attempt` alone: **ONLYOFFICE proved `apt-get update` exits 0 with an unreachable vendor host** (only `W: Failed to fetch` / "old ones used instead"), so success must be read from `apt-cache policy <pkg> | grep -q 'Candidate: [0-9]'`; and **Dropbox's keyserver key makes update exit 100 permanently** on Debian 13 (`Sub-process /usr/bin/sqv returned an error code (1) … SHA1 is not considered secure`), which is why the key must come from `linux.dropbox.com/fedora/rpm-public-key.asc` (1489 bytes, proved to satisfy both apt 3.0.3 and apt 3.2.0).

## 4. Phase boundaries

Phase 2 reserved "third-party applications" for phase 3 and "`30-conky.conf` and the conky panel" for phase 4. I would keep those anchors and **split the rest by mechanism, not by subject type** — each phase then ships one mechanism plus its tests.

**Phase 3 — vendor apt repositories, and the helper they share.** `add_vendor_repo` and `try` in `lib/common.sh`; the `install.sh` group-enumeration change; the `chromium` row pair (the only map-only subject, and the one fully apt-native route in the set); `setup-chrome.sh`, `setup-dbeaver.sh`, `setup-teams.sh`, `setup-dropbox.sh`, `setup-onlyoffice.sh`, `setup-docker.sh` (with lazydocker). Every step is independently declinable, so phase 3 ships even if any one vendor host is down on the day. lazydocker stays with Docker although it is a tarball: it is a 4 MiB static binary needing no `.desktop`, the Arch group pairs them, and `config/nvim/lua/anbar/plugins/lazydocker.lua` binds `<leader>ld` to it.

**Phase 4 — tarballs into `/opt`, and the system-level pure-apt work.** `setup-postman.sh` and `setup-tor-browser.sh` (the same mechanism: download, verify, versioned unpack, a `current` symlink, a hand-written `.desktop` and icon, and re-running the script as the update path); the Nerd Font download; the conky panel with `config/sway/config.d/30-conky.conf` restored, the i3 autostart and `$mod+Shift+t` re-added, and the two assertions in `tests/setup-sway-smoke.js` (≈ lines 130 and 172) that currently require their absence flipped; zram; btrfs snapshots; SSH hardening.

Three movements against the obvious assignment, each for a reason the findings established:

- **Postman moves out of phase 3.** It looks like an application, but mechanically it is `/opt` + `.desktop` + icon + a version flip, sharing nothing with the vendor-repo helper. Shipping it beside Tor Browser means one tarball pattern written once.
- **Tor Browser is phase 4, not phase 3.** It is the only subject whose canonical host is unreachable from this machine, and it needs a `--from-dir` staging path and a human decision about the relay. Putting it in phase 3 would block a phase on a network question.
- **SSH hardening is last in phase 4.** zram first — independent, consent-gated, cannot lock anyone out. SSH hardening last and more loudly prompted, because it is the only thing in this repository that changes how the machine can be reached, and because installing `openssh-server` starts a listening service, which nothing else here does. Its prompt belongs apart from the quiet `NetworkManager.service`/`bluetooth.service` loop.

## 5. The decisions a human still owns

- **Ubuntu's Chromium.** Debian is settled (apt `chromium`). On Ubuntu both proved routes work: Canonical's snap stub, which apt will never upgrade and which confines strictly, or Google's vendor repo, which is apt-maintained but hands the machine's trust-and-update policy to Google permanently, with a `cron.daily` that re-creates the repo. A trust call, not an evidence call.
- **Whether Teams via `repo.teamsforlinux.de` is acceptable at all** — one maintainer's host, a personal rsa4096 key with a hotmail uid — and whether the tenant permits a third-party Electron wrapper.
- **Whether Dropbox is worth installing**, given that the package is a 62 KB frontend and the usable client is a 91 MB proprietary daemon the user must fetch by hand.
- **Tor Browser's staging path**: VPS relay into `--from-dir`, a self-hosted mirror via `settings.json`, or `download_over_tor` — and whether pinning `keys.openpgp.org` as the key source is acceptable. No container can test the user's network.
- **Docker: rootless or `docker` group**, which are alternatives and must not both be offered in one run; and what to do on a machine that already has `docker.io` (I recommend refuse-and-report, but removing an engine is the user's call).
- **SSH: whether password authentication is turned off on this machine at all**, which requires confirming a working key first — and whether `openssh-server` belongs on this laptop.
- **zram size on this machine.** Raising the shipped `min(ram / 2, 4096)` cap to 8192 is the only reason to write `/etc/systemd/zram-generator.conf`, and that depends on the RAM.
- **Whether a conky panel without Nerd glyphs is acceptable** (fontconfig substitution) or worth a hand-downloaded patched font.

## 6. Risks and surprises

- **Microsoft retired the Teams client, and still serves the corpse.** `packages.microsoft.com/repos/ms-teams` verifies correctly and is deliberately empty: `Packages` is 0 bytes with the empty-string SHA256, `Release` is dated 2023-02-28, the pool is 404. Adding it buys nothing and costs a fetch on every update.
- **Arch names that do not exist in apt, each of which would break a whole group.** `conky` is a pure virtual package (`E: Package 'conky' has no installation candidate`) → `conky-std`. `zram-generator` does not exist → `systemd-zram-generator`. `docker-compose-v2` does not exist on Debian; `docker-cli` does not exist on Ubuntu. `dbeaver-ce`, `postman`, `lazydocker`, `teams` exist nowhere.
- **The 64-bit time_t transition broke declared dependencies.** `libgtk-3-0`, `libatspi2.0-0`, `libasound2` and `libappindicator3-1` print `Candidate: (none)` on both releases and resolve only as virtual provides from the `t64` packages. Consequence: a bare `dpkg -i` of the Teams .deb fails where `apt-get install ./file.deb` succeeds. Never `dpkg -i` any of these.
- **Chrome adds Google's repo whether or not you do.** Its postinst carries `REPOCONFIG="deb [arch=amd64] https://dl.google.com/linux/chrome/deb/ stable main"` and it ships `/etc/cron.daily/google-chrome`. "Install the .deb to avoid the repo" does not work; the honest options are consent or nothing.
- **Dropbox's .deb edits apt behind your back** — it writes `/etc/apt/sources.list.d/dropbox.list` over plain **http** plus its own keyring — and its postinst `rm -rf`s any `/home/*/.dropbox-dist` below version 2.10. Both suppressible with `touch /etc/default/dropbox-repo` first, which was proved to leave the package installed and apt untouched. Prefer the repository route and skip the .deb.
- **The Dropbox keyserver key is a trap**: the same fingerprint fetched from `keyserver.ubuntu.com` is SHA1-bound and rejected by Debian 13, after which a plain `apt-get update` exits **100** forever. Acceptance test for that step: `apt-get update` still exits 0.
- **ONLYOFFICE's repo quietly re-sources an unrelated package.** 308 stanzas over 71 names (DocSpace, Document Server, an XMPP server) and its `ttf-mscorefonts-installer 3.8.2` outranks Debian contrib's 3.8.1 and Ubuntu multiverse's 3.8.1ubuntu2 — watched happen in `apt-cache policy` before and after. The pin is designed, not verified.
- **`apt-get update` exits 0 when a vendor host is unreachable.** `attempt` cannot see that failure; only a candidate check can.
- **Snapper's apt hook changes the cost of every later apt step.** `/etc/apt/apt.conf.d/80snapper` takes a pre/post snapshot around *every* apt invocation the moment `/etc/snapper/configs/root` exists. Offer `DISABLE_APT_SNAPSHOT="yes"` in the same breath.
- **Versions too old to be useful.** Debian's `docker.io` 26.1.5 + Compose 2.26.1 (2024) against vendor 29.9.1 + Compose 5.6.0. Postman's snap is 11.71.7 on a core18 base — a major version and ~10.5 months behind the 12.32.3 tarball. ONLYOFFICE's snap *and* flatpak are both stuck on 9.4.0 while the repo has 10.0.0-169. `torbrowser-launcher` 0.3.7-3 ships a key that **expired 2025-07-21** with a signing subkey that expired 2024-08-23, and Ubuntu's 0.3.9 subkey `157432CF78A65729` expires **2026-10-26** — eleven days from these probes.
- **Proprietary blobs with no apt-grade integrity.** Postman publishes no checksum or signature at all (every `.sha256`/`SHASUMS256.txt` path returns 400). Dropbox's 91 MB daemon is verified only if `python3-gpg` is installed — without it the frontend prints that it will not verify and skips the check.
- **Postman's `.desktop` basename is load-bearing**: `main.js` runs `xdg-mime default Postman.desktop x-scheme-handler/postman` on every launch, so any other name silently breaks `postman://` deep links, OAuth sign-in among them. And its sandbox was only proved on an Arch kernel — Ubuntu 26.04's AppArmor restriction on unprivileged user namespaces is the one thing to test on real hardware.
- **DBeaver's .deb declares no `Depends` at all.** `dpkg` will never complain about the missing `libgtk-3.so.0`; breakage shows at first launch. GTK 3 is pulled in transitively by the existing desktop groups, so no row is needed — but a bare server would fail silently.
- **timeshift disqualifies itself**, in its own binary: "Only ubuntu-type layouts with @ and @home subvolumes are currently supported." Plus cron scheduling and GTK3/VTE/libxapp on a Sway box.
- **Every snapshot route dies on a non-btrfs root**, and nothing here knows the target's filesystem. `findmnt -no FSTYPE /` must be the first thing that step does.
- **Ubuntu universe is load-bearing** for `conky-std`, `snapper`, `btrbk`, `docker.io`, `docker-compose-v2`, `systemd-zram-generator` and `torbrowser-launcher`. A minimal install with universe off loses all of them.
- **`attempt` always returns 0**, so six steps in these two phases have no helper for "record the failure and take the other branch" — the gap `try` fills, and the likeliest source of a silent half-configured machine if it is skipped.
- **Scope of the evidence.** amd64 only (Dropbox's repo is i386/amd64 only); every version is a 2026-10-15 snapshot, and Docker's repo already showed two versions of every package, so vendor numbers in the spec should be dated where they are quoted.
- **One framing correction from the findings:** `~/arch-desktop-setup/setup-ssh.sh` does not port to SSH hardening. It is purely client-side — it writes `~/.ssh/config.d/<alias>.conf`, never touches `/etc/ssh`, and says "No connection was made." What ports is its discipline: Include-plus-drop-in instead of editing the main file, and validate a staged file before installing it. If the alias helper is wanted on Debian, it is a separate script, not a step folded into a root change to a network-facing daemon.
