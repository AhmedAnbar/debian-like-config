# debian-desktop-setup — phase 1 design

Date: 2026-09-28
Status: awaiting review
Author: AhmedAnbar

## Purpose

`arch-desktop-setup` turns a fresh Arch install into the desktop Ahmed works in
every day. This project does the same for the Debian family, so that a Debian or
Ubuntu machine ends up with the same keybindings, colours, shell and editor
rather than a second, divergent setup to remember.

Success for phase 1: on a fresh Debian stable or Ubuntu LTS desktop,
`git clone && bash install.sh` produces a working i3 session with the same look
and keys, plus the Zsh and Neovim environment, and the repository can tell which
shared configuration files have drifted from the Arch original.

## Targets

| Family | Detected by | Notes |
| --- | --- | --- |
| Debian stable | `ID=debian` in `/etc/os-release` | Oldest packages of the two; some features need a fallback. |
| Ubuntu | `ID=ubuntu` | Any Ubuntu is accepted, but only 26.04.1 LTS is verified. Newer desktop stack than Debian; apt's Firefox is a snap transitional package. |
| Mint, Pop!_OS | `ID_LIKE` contains `ubuntu` | Treated as Ubuntu. Accepted, not verified. |

Anything else exits with a message naming the two supported families, mirroring
the Arch installer's `/etc/arch-release` guard.

## Scope

In scope for phase 1:

- Repository skeleton, licence, README with the logo header, `assets/LOGO.md`.
- Release detection and the apt package map for the i3 desktop, audio, fonts,
  browser and file utilities, and the shell/editor/development group.
- `install.sh` with the same shape as the Arch one: `--dry-run`, `ask`, `run`,
  `install_file` with timestamped backups, grouped prompts.
- The configuration this phase needs, copied verbatim: `config/i3`,
  `config/i3status`, `config/kitty`, `config/rofi`, `config/picom`,
  `config/fontconfig`, `config/gtk-3.0`, `config/gtk-4.0`, `config/nvim`,
  `config/shell`, `config/flameshot`, `config/phpactor`, `applications/` and
  `zsh/`, plus `setup-zsh.sh` and `setup-nvim.sh`. `sway/`, `config/conky` and
  `config/herdr` arrive with their own phases.
- Drift control: `scripts/sync-from-arch.sh` and a test that names every shared
  file that no longer matches the Arch repository.
- Tests: preview smoke tests that run on this Arch machine, and container tests
  that resolve every apt name in real Debian and Ubuntu images.

Explicitly not in phase 1, each with its own spec later:

1. Sway/Wayland session, Waybar version guard, clipboard history, notes
   scratchpad, lock and idle behaviour.
2. Third-party applications: vendor `.deb` repositories for Chrome, DBeaver,
   Teams and Dropbox, OnlyOffice, Postman, and Tor Browser fetched through the
   VPS because torproject.org is blocked locally.
3. System extras: Docker, SSH hardening, conky, `zram-tools`, snapshots, and
   whatever replaces the Zenbook CPU cap on Debian.

## Conventions inherited from arch-desktop-setup

- `#!/usr/bin/env bash`, `set -Eeuo pipefail`, an `ERR` trap naming the line.
- SPDX `GPL-3.0-only` headers; `LICENSE` with `Copyright (C) 2026 AhmedAnbar`.
- Refuses to run as root; every privileged command goes through `sudo`.
- Existing files are backed up under
  `~/.local/state/debian-desktop-setup/<timestamp>-<pid>` before replacement.
- `--dry-run` prints every command and writes nothing.
- One README as the only documentation, with a package catalogue table that the
  tests assert is complete.
- Node smoke tests in `tests/`, run with `node tests/<name>.js`, no framework.
- Commits name Ahmed Anbar as the only author.

## The package map

`packages/apt-map.tsv` is the single source of truth: `install.sh` builds its
groups from it, the tests check every name against real apt indexes, and the
README catalogue is generated from the same rows. Columns:

| Column | Meaning |
| --- | --- |
| `group` | Prompt the package belongs to, matching the Arch installer's groups. |
| `arch` | Name in `arch-desktop-setup`, or `-` where the Debian side adds something. |
| `apt` | Package to install, or `-` when apt has none. |
| `where` | `both`, `debian`, `ubuntu`, or `none`. |
| `note` | Why it differs; required whenever `arch` and `apt` differ or `where` is not `both`. |

A row with `where=none` must name its replacement in `note`; phase 1 either
implements that replacement or defers it to a later phase explicitly.

## install.sh

Order of operations, each step refusable:

1. Guards: not root, `apt-get` present, `/etc/os-release` names a supported
   family, the bundled `config` directory is beside the script.
2. `sudo apt-get update`, then one `sudo apt-get install` for the accepted
   groups, so a declined group costs nothing.
3. Configuration files through `install_file`, with backups.
4. A closing summary: what was installed, what was skipped, what to do next,
   and which steps belong to a later phase.

`install.sh` reads the release from `${DEBIAN_SETUP_OS_RELEASE:-/etc/os-release}`
so the tests can simulate Debian and Ubuntu on this Arch machine without
containers.

## Drift control

`scripts/shared-files.txt` lists every path that must be byte-identical to
`arch-desktop-setup`; `scripts/adapted-files.txt` lists the paths that must
differ, each with a one-line reason. For phase 1 that is `config/i3/config`,
whose autostart comment links the Arch wiki, and `config/i3/emoji.sh`, which has
to cope with `rofi-emoji` not being packaged.

`scripts/sync-from-arch.sh` takes `--check` (default) or `--pull`:

- `--check` prints one line per file: `same`, `drifted`, or `missing`, and exits
  non-zero on drift, so it is usable from a hook or by hand.
- `--pull` copies drifted shared files from the Arch checkout, refusing to run
  when the working tree is dirty, and backing up what it replaces.

The Arch checkout is `${ARCH_SETUP_DIR:-$HOME/arch-desktop-setup}`. When it does
not exist, `--check` says so and exits 0, so a fresh Debian machine that has
never held the Arch repository is not blocked by this tooling.

## Tests

| Test | Runs where | Asserts |
| --- | --- | --- |
| `install-smoke.js` | Anywhere with bash and node | Dry-run previews for a simulated Debian and Ubuntu produce the expected apt names; guards reject root, an unsupported `ID`, and a missing `config` directory; a preview writes nothing. |
| `drift-smoke.js` | Skips without the Arch checkout | Every file under `config/` appears in exactly one of the two lists; shared files match byte-for-byte; adapted files really differ and carry a reason. |
| `apt-names-smoke.js` | Only with `DEBIAN_SETUP_CONTAINER_TESTS=1` and docker | Every `apt` name with `where` covering that release resolves to a candidate version, and `apt-get install --simulate` succeeds for the full accepted set. |

The container test is gated behind an environment variable because it pulls
images and takes minutes; the other two stay fast enough to run on every change.
A skipped test prints why it skipped rather than passing silently.

## Logo

`assets/LOGO.md` holds a prompt written by the codex CLI, following the Arch
repository's convention of recording the prompt beside the asset. Ahmed generates
the image in ChatGPT from that prompt and saves it as `assets/logo.png`; the
README header references that path at 240px with descriptive alt text, so the
image link is broken until the file is added, which is its own reminder.

The prompt asks for a Debian-family counterpart to the Arch mountain logo: the
same tiled-panel, flat, minimal language, in Debian red against the Catppuccin
dark background, readable at README icon size, no text, and no replication of the
official Debian swirl.

## Risks

- **No GUI in containers.** Container tests prove package names and apt
  resolution, not that i3 starts. Phase 1 therefore claims only what it can
  show; the desktop itself is confirmed on the first real Debian machine.
- **Debian stable is old.** Where a package predates a feature the configuration
  needs, the map's `note` column records it rather than silently shipping a config
  that fails. Waybar is the case that matters: Debian carries 0.12.0 while the
  calendar block in this desktop was written against 0.15, which Ubuntu 26.04
  already has. The guard is therefore Debian-only, and belongs to phase 2.
- **Ubuntu's snap Firefox.** On Ubuntu 26.04 apt's `firefox` is the transitional
  snap package `1:1snap1-0ubuntu9.1` and `firefox-esr` does not exist; Debian is
  the reverse. Phase 1 installs `firefox-esr` on Debian and defers Ubuntu's
  browser to the vendor repository work in phase 3 rather than pulling in snap.
- **Neovim version.** Ubuntu 26.04 ships 0.11.6, which this configuration is
  happy with; Debian stable ships 0.10.4. `setup-nvim.sh` installs the upstream
  tarball into `~/.local/opt` when apt's version is older than 0.11, and reports
  which source it used.
- **No `rofi-emoji` in either release.** This one cannot be deferred, because
  phase 1 ships the i3 configuration whose Super+period binding calls it. The map
  marks it `where=none`, and `config/i3/emoji.sh` becomes an adapted file that
  reports the picker is unavailable instead of failing silently, the same pattern
  `clipboard.sh` uses for a missing `cliphist`. Building it from upstream is a
  phase 2 decision; the binding behaving predictably is a phase 1 requirement.
- **Names verified, behaviour not.** A resolved apt name is not a working
  desktop. Everything this phase claims is limited to what a container can show:
  resolution, simulated installation, and file placement.

## Decisions still open

- GitHub repository name and whether to push at all; nothing is pushed without
  being asked.
- Ubuntu 26.04.1 LTS is the reference release, being what `ubuntu:latest`
  resolved to during verification; Debian 13 trixie is the Debian reference.
  Older Ubuntu LTS releases are untested and unclaimed.
